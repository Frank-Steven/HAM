# HAM 4.0 概述

## 序言

自 HAM 3.0 提出以来，理论的完备性一直都是 Frank Steven 和 Castle 不断尝试证明却始终没有达到的目标，HAM 3.0 在较早的时候就被证明可以用于动态类型系统的函数式编程，但是为了工程上的类型安全、类型检查、泛型等本该有的高级特性以及在 CPU 上的执行效率，我们引入了很多概念，并试图证明。

但是，无限展开的集合与递归成为了我们走向类型安全的一块巨大绊脚石，而神谕的设计也一直没有头绪，经过苦思冥想也迟迟没有结果。

一天，Frank 在翻看聊天记录时，一条极为简短、没有什么内容的感叹在他的脑中发生了化学反应：

> “我突然想到一种比喻，函数式编程是一种‘四维生物’体验”

巧合的是，这几天，他正在玩游戏“图灵完备”（一个用基本逻辑门电路拼计算机的游戏）、研究 LLVM IR 的语法和一些他看不明白的范畴论内容，所以一个想法应运而生：如果说 HAM 的 Monad 值就是一个静态的程序框图呢？这彻底改变了他对函数递归的看法——或许递归其实并不存在，存在的只是一个简单的“循环结构”。

HAM 4.0 用一种类似范畴的东西作为新的类型，这让原来只有一层的集合变成了可以向上推广到函数的新类型量，用 LLVM IR 的控制流模型作为 Monad 中程序框图的可组装节点，并把一切值的产生作为 Monad 控制流的职责。于是，HAM 可以充分处理各种各样的类型，最后的“临门一脚”灵感源于和班主任的谈话，谈话中，同样作为编程语言研究爱好者的他感叹道：确实现在好多语言都不是一门“设计出来”的语言，一个语言想要完美是几乎不可能的。

Frank 意识到语言之所以要类型安全，就是因为语言是给人写的（尽管现在有很多 AI 用于生成代码，但 AI 写的代码和人类写的代码差别不会太大），所谓类型安全、类型检查，就是为了防止写代码的人搞砸一些很显然的事情，与其追求那个早就被数学证明不可行的 100% 理论安全，除非放弃图灵完备，否则可谓是天方夜谭。于是，HAM 最终选择了在一定程度上相信程序员，引入了 unsafe 机制，这才让 HAM 的安全类型检查形成闭环。

虽然看起来像是无奈之举，但 HAM 并没有放弃高级语言特性，所以说这一决策直接导致了这一版本的 HAM 的确立，他认为这个版本反而最接近他最初创造 HAM 时的想法：充分利用函数式的优点，打造工程友好、性能卓越的函数式语言。

## HAM 4.0 基本模型

### 1. 函数

函数的定义是一个依赖一组未知表达式的新表达式，这些表达式都需要指明自己所属的范畴（由于不可判定性，函数不能被集合包含，因此此处的范畴对于函数来说是一种约束，约束其所依赖的表达式所属的范畴和其表达式本身所属的范畴，或者说是一种箭范畴，可以理解为函数是集合的态射，而此处对函数的约束就是从这里得出的箭范畴），范畴参与类型推导，但本身不能作为集合使用。

### 2. 范畴

在 HAM 3.0 的后期就已经有这种集合的概念，当时称这种集合为“约束”或者“HAM 特色集合”，这个版本我们将其正式定名为范畴。

范畴是对元素的约束，应用位置在函数的两端或者手动使用 `in` 等运算符判定一个表达式是否属于某个范畴。本来，范畴本身也可以作为一种表达式，并具有其所属的范畴（类型范畴）。虽然如此，能够直接应用于类型的运算及其少，只有并、且、非等逻辑运算，所以类型范畴只有一个，不能对类型进行特殊的分类操作。HAM 在编译的时候会倾向于在编译期完成类型检查，并在不安全区域未启用时拒绝无法确定对象是否属于的可判定性的范畴。

### 3. 组合

组合是 HAM 用函数式程序组织有层次的代码的基石，且用自然的方式将不可变模型、经典赋值、函数和运算符重载、面向对象的继承与多态等高级思想以一种和谐的方式统一为一个以“覆写”为基础的操作。HAM 4.0 彻底将组合拆散，从而避免在层层嵌套时产生的复杂类型问题，然而，这并不妨碍你用一种整体的概念而不是分层的概念来理解 HAM 中的组合，只是现在组合只是一种框架，不会有真正的组合参与运算，参与运算的是组合内部的值，在运算的时候，组合会拆成一组不同的表达式同时参与某一项运算（取值运算 `.` 除外）。

### 4. 神谕

HAM 3.0 始终没有解释清楚的部分，也是决定了 HAM 4.0 能够在理论上完备地实现类型安全和全程序编译的关键，从某种意义上是 HAM 3.0 和 HAM 4.0 之间划时代的变化。HAM 4.0 的神谕紧紧围绕 LLVM IR。从常量到变量、从纯函数和控制流完全定义 HAM 的函数式控制流变换语义。

> 函数、范畴和组合可以任意组合产生丰富多变的语法语义，神谕的实现原理落实 HAM 4.0 从逻辑上完全支持任何组合方法
